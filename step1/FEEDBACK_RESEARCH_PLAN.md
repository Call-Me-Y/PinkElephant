# 下一阶段：根据证据与恢复进展生成反馈

状态：研究建议，尚未实现或运行新方案。已有48个失败点作为开发与诊断集，不作为后续独立确认集。

## 研究问题与现有证据

建议的问题是：失败之后，如何选择并传递恢复所需的最少信息，使智能体保留正确事实、补齐未完成目标，
同时减少失败动作表面形式的干扰？这比单独修改正向提示措辞更适合形成一条连贯的研究路线。

当前历史正向提示相对FTB抽象，上游成功为17/48 vs 11/48；补充目标核对为10/48 vs 8/48。
后者配对差值+4.2个百分点，任务聚类95%区间[-6.3,+16.7]个百分点。只有改善趋势，尚未证明稳健优势。
解码排斥降低了重复，未稳定提高任务成功；正确动作监督的改善更大，额外UL没有独立收益。

现有代码有三个具体限制：

1. `feedback.py`按错误类别选通用模板；缺参数时额外指出字段，但基本没有使用目标要求与已确认事实。
2. 历史的作用主要是计数，第二次失败才增加一条通用检查要求。
3. 任一工具成功都会清空未解决窗口；它不等于任务恢复，可能仍有错误实体、错误主题或偏离目标。

## 推荐的核心方法

先实现“事实记录—未完成目标—反馈编译”三个小模块。首版用规则，不先训练大模型或增加复杂检索。

### 1. 记录事实来源，区分目标与当前状态

每条记录至少包含：事实字段、值、来源、对应观察编号、当前是否有效、与哪个目标要求有关。
事实的合法来源为用户要求、公开工具schema、成功查询结果、可由成功执行与工具契约共同确认的状态变化。
失败动作中的参数只能作为内部待核实假设，不能自动提升为已确认事实；报错中的候选建议也应先核实。

成功执行的错误操作会产生真实状态，但不是正确目标。例如“消息发给B了”不能推出“目标收件人是B”。
因此反馈需要同时做来源校验和目标相关性选择，不能直接重放所有成功调用。
工具结果改变或与旧事实冲突时，旧记录失效。

重要的表示修正：正确邮箱等事实可能也曾出现在失败调用里。只要其独立来源是用户目标或成功查询，
就允许作为恢复证据使用。不能用“与失败调用有任何token重合”作为禁止条件，否则会删掉正确信息。
仍应限制完整失败调用和仅由失败动作引入的错误值。此限制不保证失败动作在信息论上不可还原。

### 2. 从“错误类别”转向“尚未满足的要求”

从用户目标和公开工具定义提取要求，不读取 `task.gold_actions`、隐藏payload、测试脚本或隐藏世界状态。
对每个要求记录：已有证据、缺失证据、可由什么公开观察验证。
工具返回ok只更新相应状态；只有相关要求有证据满足，才关闭该项恢复记录。

例如发送文件：目标联系人、明确主题、完整文件内容、发送完成分别是不同要求。
缺少body且已读取文件时，应引导复用该读取结果；尚未读取文件时，应引导先获取内容。
同一错误类别可以对应不同的下一步，正是现有类别模板缺少的区分。

### 3. 编译简短正向反馈，按结果更新

内部结构建议为：

```text
remaining_requirement: 当前尚未满足的具体要求
verified_facts: 本次恢复需要的事实及来源
missing_evidence: 仍需查询或确认的信息
next_subgoal: 下一步应达到的状态
completion_check: 可用公开工具结果核对的条件
previous_hint_outcome: 上次提示是否被执行、是否推进目标
```

给actor的反馈先控制在80–120个英文token以内，保持任务原语言。
内容可以包含合法事实、字段约束和下一步子目标；不生成完整参考调用，不提供隐藏正确答案。

示意：

> 继续完成发送文件的请求。收件邮箱已由联系人查询确认；主题应使用用户指定的agenda。
> 正文使用最近一次read_file返回的完整内容。下一步完成发送；以目标收件人、主题和正文均匹配作为完成依据。

事实的具体值若需要重提，必须从记录的合法来源取值，而不是从失败动作复制。
引用观察编号与直接重提事实值应分别测试：原上下文中已存在这些信息，重提可能只是降低了检索负担。

历史用于区分三种情况：前次提示未被执行、已执行但没有推进、已有推进但剩余要求未完成。
分别选择重申关键要求、补充证据/切换子目标、保留进展继续下一项。不要仅随失败次数增加文字强度。

## 让方法能够被证伪的机制测试

1. 固定目标、成功观察、错误类别，仅改变无关的失败动作写法或错误值；反馈应保持不变或语义等价。
2. 固定错误类别，改变可用证据：已经查到ID vs 尚未查询，反馈应正确切换“使用已确认ID”和“先查询”。
3. 固定失败次数，改变此前提示是否执行、是否推进，检查历史策略是否给出不同且合理的下一步。
4. 移除来源校验、目标要求或历史响应记录，检查增益来自哪个模块。
5. 使用过时或无关事实做受控干扰，检查选择器是否会把错误信息注入反馈。

“对错误表面形式不敏感”本身FTB抽象也有；我们需要证明更具体的反馈在保留这种性质时仍提高恢复效用。
自动字面重合审计不等同于语义隔离证明；人工检查事实来源、错误值转述和可重建性。

## 提示生成可以怎样自动优化

先固定JSON结构、来源规则与预算，只优化“如何选择字段和表达下一步目标”。
在开发集上可借用GEPA或TextGrad优化生成器的通用指令；它们属于优化工具和强对照，不能直接作为独创贡献。
训练/开发过程的失败轨迹可以给优化器读取，确认集轨迹不可用于更新生成器。

若规则版有可复现增益，再训练小型反馈选择器：在训练世界中对同一失败点分叉，
比较“诊断”“诊断+目标”“诊断+目标+必要事实”“补证据请求”等卡片，观察实际恢复。
以严格目标推进、重复、错误事实与成本给候选打分；学习何时使用哪种反馈。
测试时选择器仅看到运行时证据，不能试完所有候选后用隐藏成功标签择优。
避免将模型自己声称“建议很好”的评分直接当作成功；优先使用环境执行和可观察目标变化。

## 必须保留的对照

| 条件 | 作用 |
|---|---|
| 无反馈/删除失败记录 | 比较新增信息是否确有必要 |
| FTB原版abstract | 最近邻强基线 |
| 当前历史正向模板 | 衡量新生成器的增量 |
| 只重提目标与已确认事实，不给修复建议 | 分离信息重提与纠错策略收益 |
| 直接让同一个LLM根据完整轨迹生成正向建议 | 控制额外模型能力与调用预算 |
| 新结构：必要事实+未完成要求+下一步子目标 | 完整表示，但不使用自适应历史 |
| 完整方法：加上提示执行/恢复进展状态 | 单独检验历史是否有额外价值 |

内容比较先固定相同失败触发点和观察窗口；不要让新方法独享更强检测器或更多提醒机会。
之后再单独评测目标偏离检测与闭环更新。额外查询、监控模型调用和actor调用全部计入预算。
Sentry比较使用其原有检测/修复/验证流程；只有进入同一公平条件的组件才作可归因比较。

接入Sentry时，先固定检测器、playbook和验证器，只替换反馈生成及actor轨迹渲染。
至少比较原Sentry、Sentry+FTB式失败轨迹抽象、同一抽象轨迹+新反馈生成器三组。
只修改 `repair.prompt_text` 而在actor历史中保留原失败调用，不能称为动作内容隔离。
相反，只因删除了失败轨迹获得的增益，也不能全部归因于新的正向提示生成器。

## 数据与评价

现有48条只用于开发。固定新规则后，在未用过的任务世界进行确认。
另外收集actor自然生成的失败，对同一个真实失败前缀分叉各方法。每个模型先做模型内配对，
避免不同模型的自然失败难度差异被误当成模型尺度效应；共享受控集可作补充。

优先包括三类失败：接口错误、实体/事实错误、合法调用但未推进或违反任务要求。
在开发时预先固定完整目标判据；确认集不再用结果调整规则。保留原FTB分数便于对照，新增目标核对明确标记。
运行时生成器不访问隐藏评测判据，任何隐藏标签只用于离线评价或独立训练数据的学习。

主指标为任务成功和真实失败后的恢复；同时报告原错重复、新错重复、错误事实暴露、目标偏离、
提示执行率、恢复步数和总token/调用成本。工具成功不代表任务恢复，提示执行也不代表提示有帮助。
按独立任务聚类给配对差值与区间，不能把多个历史或多个分叉当作独立样本。
样本量根据开发集配对差值方差确定；可先准备100–200个自然失败检查点，不能保证这个数量必然得到显著结果。

首个现实任务域沿用已有AppWorld运行环境；模型使用现有0.5B开发，9B或一个可用API模型做关键验证。
LLM版监控器与actor尽量复用同一服务顺序调用，并给直接LLM建议基线相同模型/调用预算。

## 与已有工作的关系及可能贡献

Reflexion已有反思记忆，CRITIC已有工具反馈驱动的修正，Sentry已有条件检索、恢复验证和验证后记忆写入。
仅加监控器、使用外部记忆或验证修复，不能作为独立新颖性主张。
GEPA和TextGrad已有自动提示/文本优化，所以“自动优化正向提示”也需要更具体的问题和证据。

潜在贡献可聚焦为：

- 面向失败恢复，按证据来源选择性保留正确事实，同时限制失败专属内容的反馈表示与编译过程；
- 对错误表面扰动不敏感、对证据缺失和历史响应敏感的可测性质，以及恢复效用/信息暴露/预算之间的权衡；
- 在同前缀真实失败上拆分信息重提、引导策略和历史适应的收益，并在独立任务及更强模型上验证。

这是一条待验证的研究路线，尚不能确认新颖性或保证发表；若只重提事实的基线与完整方法持平，
贡献应收敛到证据提取与信息通道，而不能宣称学会了新的恢复策略。

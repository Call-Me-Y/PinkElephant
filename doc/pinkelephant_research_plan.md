# PinkElephant：多步智能体中的无失败动作纠错记忆

## 一句话研究主张

多步智能体需要从失败中恢复，但把失败动作原样放入后续上下文可能增加重复概率。PinkElephant 研究一种**动作内容隔离的纠错记忆**：监控器可以读取完整轨迹来判断发生了什么，写入记忆与注入给任务智能体的纠错卡片则不得复述、引用或重建失败动作；系统只在相似失败再次出现时检索经过验证的修复原则，并检查后续行为是否恢复。

这个主张比“把错误信息改写成自然语言”更具体。已有工作已经报告，单纯用运行时生成的失败描述替代原始失败调用可减轻重复效应；Sentry 也已经实现失败触发的外部 playbook、恢复验证和跨任务积累。因此，PinkElephant 的核心贡献应落在**动作排除的表示与信息通道、可验证的动作泄漏标准，以及它在多步任务中是否既减少重复又保留纠错收益**，而非笼统声称首次提出按需反馈或失败记忆。

## 改良后的项目表述

### 中文学术版

多步智能体通常通过将工具调用及其运行结果追加到交互轨迹中来处理执行失败。然而，失败调用的表面形式可能在后续上下文中形成强烈的复现线索，使负面反馈反而提高智能体重复同一错误行为的概率；完全移除失败上下文又可能丢失诊断所需的信息。PinkElephant 拟研究一种**动作内容隔离的纠错记录与处理框架**：系统在内部依据完整轨迹识别失败类型和状态变化，但将可复用的纠错知识编译为不包含失败动作内容的结构化记录；仅当后续轨迹满足相应触发条件时，系统才向任务智能体提供简短的状态约束、修复目标或下一步决策原则，并通过后续环境状态验证纠错是否奏效。我们将系统性评估该框架在降低同错重复率的同时，能否维持或提升纠错成功率、任务完成率与跨任务迁移能力，并与原始错误回显、文字化反馈、反思记忆及运行时干预方法进行对照。

### 简短摘要版

PinkElephant 面向多步智能体的失败恢复，研究如何在不向任务智能体复述失败动作的条件下保留有效纠错信号。框架从完整执行轨迹中抽取失败类型、触发状态和经验证的修复原则，将其存入外部结构化记忆；当相似失败再次出现时，系统按当前状态检索并提供动作内容隔离的纠错卡片，再依据后续环境反馈验证恢复情况。研究将通过受控重复实验与 WebShop、AppWorld 等多步基准，检验动作重复、恢复率、最终任务表现、误干预和跨任务迁移。

## 文献脉络与研究空缺

| 方向 | 代表工作 | 对 PinkElephant 的启示 | 仍需回答的问题 |
|---|---|---|---|
| 失败动作回显与复制效应 | Gumaan, *Feedback That Backfires*（2026 年 8 月 arXiv 预印本；项目 literature 中的 PDF） | 在小型指令模型、模拟工具调用和 MBPP 修复中，失败记录会提高失败动作再次出现的概率；反事实分解将主要效应归因于失败动作字符串在上下文中的出现。文中报告运行时生成的失败描述可减轻大部分反转。 | 该结论能否推广到更强模型、长时程真实任务和语义级“重复动作”；动作内容隔离的记忆能否跨任务学习、在条件匹配时生效，并不牺牲成功修复？ |
| 语言反思和经验记忆 | Reflexion（Shinn et al., 2023）、ExpeL（Zhao et al., 2023） | 说明无需更新模型参数，也可将反馈总结成自然语言经验并供后续尝试使用。 | 反思可能包含失败动作、在不匹配情境中误用，且通常没有显式的动作泄漏约束或恢复准入验证。 |
| 条件检索的恢复记忆 | Sentry（Ji et al., 2026 年 10 月 arXiv 预印本；项目 literature 中的 PDF） | 外置 playbook、失败时检索、恢复后才写入，已在 WebShop、AppWorld、SWE-bench Lite 及 Mind2Web Replay 上评估；也是 PinkElephant 最近、最重要的比较对象。 | Sentry 的一般原则已与“按需外置纠错记忆”重合。PinkElephant 必须更严格地定义纠错通道不得传递失败动作内容，并量化这种隔离带来的重复率变化、效用和泄漏风险。 |
| 运行时监控与干预 | AgentGuard、AgentFixer、Wink、AgentForesight 等（Sentry 的基线综述与比较覆盖其中多种） | 说明运行时监控可定位无效动作、停滞与不 grounded 的推理，并在执行中干预。 | 固定规则或即时干预的知识积累、误报代价、触发条件迁移仍是关键比较维度。 |

**定位判断：**“反馈应条件触发”“知识放在外部记忆”“只记录成功修复”都不能单独作为 PinkElephant 的新颖性主张，Sentry 已覆盖这些点。建议将研究问题写成：**能否通过动作内容隔离的纠错表示与通道，在多步执行中同时降低失败动作的再现、维持有效恢复，并将已验证的修复原则迁移到后续相似失败？** 这仍需通过完整的相关工作检索和复现实验确认新颖性，不宜在立项阶段宣称已有绝对空缺。

## 建议的方法：Action-Free Correction Memory（AFCM，动作内容隔离纠错记忆）

PinkElephant 是整体工作框架名；AFCM 可作为其中的方法模块名称。每条记录不是失败动作的摘要，而是面向失败条件的状态—修复知识。建议从可解释、可审计的结构化版本开始：

```text
failure_family: schema_rejection | no_progress | state_mismatch | unsupported_plan
trigger: 可由环境状态或近期轨迹判定的条件
state_signature: 失败发生时可观察的状态特征，不含动作文本
repair_goal: 下一步应达到的状态或决策目标
repair_principle: 一条简洁的正向策略
success_criterion: 可从环境反馈判定的恢复条件
provenance: 来源任务、验证次数、置信度、适用环境
```

明确禁止字段：原始调用、参数、代码行、复制的报错片段，以及能够直接反推出失败动作的逐字近似描述。工具名或动作类别只有在必要且不会暴露原动作时才保留；具体约束需要在实验前定义，并报告不同严格度的敏感性分析。例子：对“连续查询未缩小候选范围”的失败，不保存原查询字符串，而保存“当前候选集合连续两步不变；下一步选择尚未检验的属性维度，并检查候选集合是否收窄”。这给出可执行的决策方向，却不重复原始错误调用。

### 运行流程

1. **记录完整轨迹。** 执行器保留 agent、工具、观察和环境状态，用于判断是否出现失败。
2. **检测并分类。** 监控器读取轨迹，识别 schema 错误、无进展、状态不匹配、无依据计划等失败，并提取可观测状态签名。检测器可看见失败动作，但它的输出要经过隔离编译器。
3. **编译动作隔离卡片。** 编译器将诊断映射为结构化状态条件与修复目标，不将失败动作或可逆向还原的细节送入任务智能体。首版优先使用环境提供的结构化错误类型、状态变化、工具 schema 校验结果；仅在缺少结构化信号时才用语言模型抽取。
4. **按需检索与引导。** 只有当前失败匹配触发条件时，检索少量高置信记录。向 agent 发送“当前观测状态 + 修复目标 + 正向策略 + 成功条件”，不发送历史失败动作。无匹配记忆时使用通用、同样不回显动作的修复模板。
5. **恢复验证。** 观察之后若干步，判断失败模式是否停止且任务是否恢复有效推进。只将通过验证的修复知识写入记忆；反复失败的条目降低置信度或隔离，避免把错误建议传播到后续任务。
6. **动作泄漏审计。** 编译后自动检查与原失败动作的字符串重合、关键参数重合；对样本做盲测，让标注者只看纠错卡片并判断能否还原失败动作。自动过滤不能替代人工/模型盲测，因为语义重述仍可能泄漏。

### 核心假设

- **H1（重复抑制）：** 相比“失败动作 + 原始错误”回显，AFCM 降低同一失败动作的精确重复率和语义等价重复率。
- **H2（纠错保留）：** AFCM 的恢复率和最终任务成功率不低于等 token 预算的文字化失败说明；若能减少重复而保持恢复，才算核心目标达成。
- **H3（条件匹配）：** 失败触发检索优于把完整 playbook 常驻上下文，尤其在相似表象对应不同正确处置的任务中。
- **H4（验证准入）：** 只写入已验证的修复记录优于无门槛地记录所有失败反思，提升 held-out 任务表现并降低有害干预。

## 实验设计

### 阶段一：受控因果复现

复现 *Feedback That Backfires* 的失败调用重复测量，并扩展到多步环境。固定任务、初始状态、模型、采样种子和 token 预算，对每个错误点 fork 相同前缀，比较以下条件：

| 条件 | 任务智能体看到的反馈 |
|---|---|
| C0 无纠错 | 仅收到中性、最少信息的执行结果 |
| C1 原始回显 | 失败动作与原始错误，代表常见 ReAct 式 harness |
| C2 失败动作 + 纠错提示 | 原始回显，并明确要求不要重复，检验负向指令是否足够 |
| C3 文字化失败描述 | 不回显原始动作，由运行时生成自然语言摘要，对齐前作的摘要基线 |
| C4 Sentry 式检索修复 | 当前诊断、检索 lesson 与软修复；按公开实现尽量复现 |
| C5 PinkElephant/AFCM | 只提供动作隔离卡片；外部记忆按失败状态触发 |
| C6 内容消融 | 保留与 C5 相同框架，分别去掉 state signature、repair goal、验证准入或条件检索 |

C0 用来判断“不让看到原动作”是否只是丢掉有用信息；C3 是极其重要的近邻方法，防止只与原文回显做弱比较；C4 区分方法增益究竟来自 Sentry 已有机制还是严格的动作隔离。除最终任务指标外，应在每个失败点执行局部配对 fork，以估计单次纠错的因果效果。

### 阶段二：基准评测

| 优先级 | 基准 | 用途与注意事项 |
|---|---|---|
| 首选 | **WebShop** | 多步商品检索与购买；可观察搜索停滞、重复筛选和目标匹配后未完成等失败。按固定 task split 和多个运行种子比较平均 reward、满分成功及触发后的恢复率。 |
| 首选 | **AppWorld** | 有状态、多应用 API 任务；检验纠错在长链工具调用、参数错误及副作用环境中的泛化。使用任务测试通过率，并报告误修改/非预期状态变化。 |
| 机制基准 | **MBPP 程序修复** | 沿用 *Feedback That Backfires* 的变异程序与真实 interpreter 反馈，直接测量失败代码/工具动作回显效应。先做干净复现，再测试 AFCM。 |
| 机制基准 | **Mind2Web Replay** | Sentry 对 Mind2Web 做了允许 rejected action 后重试的 Replay 适配，适用于控制网页任务中的局部恢复。明确这是适配版，不能把分数与官方 Mind2Web 步级指标直接对比。 |
| 扩展 | **SWE-bench Lite** | 作为高成本代码 agent 外部验证；失败诊断需控制模型、工具预算、容器和官方评测设置。适合在前述机制成立后再投入，不建议作为首个 benchmark。 |

最小可行论文实验：先完成受控复现（工具调用 + MBPP）与 WebShop、AppWorld 两个多步基准；再做 held-out 记忆迁移和至少一个外部域（Mind2Web Replay 或 SWE-bench Lite）。如沿用 Sentry 的 Replay 设置，标清楚它属于新增的交互适配。

### 基线与公平性控制

- 基线：原始 agent、C1 原始反馈、C3 文字化摘要、Reflexion 或 ACE 类反思/上下文演化、Sentry、AFCM。
- 采用相同任务 agent、模型版本、system prompt、环境版本、动作预算、上下文预算与采样设置；检测器/修复生成器的模型与调用成本单独报告。
- 先做 online-from-scratch（记忆为空，跨任务累积），再做 held-out（训练任务与评测任务不重合），检验迁移，避免把任务记忆泄漏误当作纠错能力。
- 使用至少 3 个随机种子，优先 5 个；方法间任务与种子配对。置信区间按任务聚类 bootstrap，报告均值、95% 区间与效应量。Sentry 使用 5 次重复的做法可作对齐参考。
- 同时给出相同 token 预算与相同模型调用预算下的结果；以免更长的引导文本或额外 LLM 调用带来不公平优势。

### 指标

**主指标**

- 任务成功率/环境主指标（WebShop reward、AppWorld test pass 等）。
- 失败后恢复率：相同失败模式在预定观察窗口内停止，且 agent 恢复与目标相关的有效推进。
- 错误动作重复率：精确字符串重复；语义等价重复（由环境状态/动作语义规则优先判定，模型裁判只作补充）。

**诊断指标**

- 恢复所需步数、无效动作数、干预精确率/召回率、误干预率。
- 动作泄漏率：卡片字面包含失败动作内容的比例；盲测可还原率（读卡片者能否识别被排除动作）；错误参数或代码片段暴露率。
- 负迁移率：被触发的 lesson 在当前情境中导致停滞、回滚或任务失败的比例。
- 每任务 token、模型调用数、延迟与成本；记录规模增长和检索命中率。

## 成功判据与可证伪性

PinkElephant 的最低成功标准不应只是“卡片不含原文”。建议预注册以下判据：

1. AFCM 对 C1 显著降低精确和语义重复率；
2. 对 C3（文字化摘要）也有清楚的增益，或在重复率相当时提升恢复率/任务成功率；
3. 主任务成功率相对 C1 提升，并且相对 C3、Sentry 至少在某一关键维度有统计上可靠的优势；
4. 卡片盲测可还原率低，同时恢复效用不依赖泄漏失败动作；
5. held-out 任务上有效，且误干预与调用成本可接受。

若 C5 仅达到 C3 同等效果，应将贡献收敛为一种更严格、可审计的安全表示与测量协议；若卡片移除动作信息后恢复率明显下降，则应报告信息—干扰权衡，进一步测试哪些最小状态特征足以恢复效用，而不能把动作抑制单独当成成功。

## 建议实施顺序

1. **第一周：** 读取两篇项目文献及其公开代码；实现失败动作重复测量、轨迹分叉和条件记录格式；确定动作语义等价与泄漏审计定义。
2. **机制验证：** 在模拟工具调用和 MBPP 跑 C0–C5 小规模配对实验；据结果调整卡片 schema，避免投入完整任务 benchmark 后才发现信息损失。
3. **集成评估：** 接入 WebShop、AppWorld；固定模型、split、预算和种子；加入 Sentry/C3 对照与 AFCM 组件消融。
4. **迁移与审计：** online 与 held-out 分开报告；盲评卡片可还原性；核对记忆增长、重复 lesson、误触发和推理开销。
5. **发布：** 提供 runner、schema、任务/种子清单、逐失败事件日志和指标脚本；公开基准适配差异，尤其是 Mind2Web Replay 的非官方性质。
